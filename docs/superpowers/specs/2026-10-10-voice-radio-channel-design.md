# Голосовая рация Orbitra

## Цель

Добавить отдельный голосовой режим рации. Игрок удерживает настраиваемую клавишу радио-PTT, говорит в выбранный канал обычной рации, а сервер доставляет голос только игрокам, которые имеют право слушать этот канал. Голос рации должен восприниматься как передача через устройство, а текущая локальная речь рядом с персонажем должна продолжить работать без изменений.

## Границы

В эту функцию входят:

- отдельная клавиша `RadioPushToTalk`;
- синхронизация голосового канала с выбранным каналом обычного радио-чата;
- серверная проверка канала и прав говорящего;
- доставка голосовых пакетов по подписчикам радиоканала;
- отдельная обработка и буферизация радиоголоса на клиенте;
- состояние передачи и карточка говорящего в HUD.

В эту функцию не входят изменение текстового чата, новые радиоканалы, изменение гарнитур или изменение proximity-голоса.

## Пользовательский поток

1. Игрок выбирает канал обычной рации через существующий селектор чата.
2. Игрок удерживает отдельную настраиваемую клавишу радио-PTT.
3. Клиент отправляет голосовые кадры с режимом `Radio` и идентификатором выбранного канала.
4. Сервер проверяет, что говорящий жив, подключён к персонажу, канал существует и канал доступен его активной радиосистеме.
5. Сервер отправляет кадр только слушателям того же канала. Получатель определяется по `ActiveRadioComponent`, включая `ReceiveAllChannels` и `GlobalReceive` по действующим правилам радиосистемы.
6. Клиент воспроизводит такой кадр через радиопуть, показывает индикатор передачи и карточку говорящего в доступной правой области HUD.

Если выбранный канал недоступен говорящему или канал не выбран, радио-PTT не отправляет голос. Клиент сбрасывает устаревший выбор на `Common`, когда выбранный канал больше не доступен.

## Архитектура

### Общий протокол

Расширить `MsgOrbitraVoiceFrame` полями:

- режим передачи: `Proximity` или `Radio`;
- идентификатор `RadioChannelPrototype` для режима `Radio`.

Для обратной совместимости отсутствие режима трактуется как `Proximity`, а отсутствие канала не допускается для `Radio`. Существующий `UnreliableSequenced` и отдельный sequence channel сохраняются. Пакет не должен содержать текст, имя канала из клиента или произвольные права доступа.

### Сервер

`OrbitraVoiceChatSystem` разделяет обработку на два маршрута:

- `Proximity`: текущая доставка в радиусе с позиционным расстоянием;
- `Radio`: проверка канала и доставка через фильтр подписчиков радиосистемы без позиционного ограничения.

Для проверки прав используется тот же источник, что и у текстовой рации: активные `ActiveRadioComponent` на сущности персонажа и её инвентарных/релейных устройствах. Проверка выполняется на сервере для каждого входящего радио-кадра; клиентскому выбору канала доверять нельзя. Говорящий должен иметь право передавать в выбранный канал, а получатель — право принимать его. Общий канал использует существующий `Common`.

Маршрутизация не вызывает отправку текстового сообщения через `RadioSystem.SendRadioMessage`: голос не должен создавать дублирующую строку в чате. Она переиспользует правила доступности радио и обычный PVS/сетевой фильтр для адресатов.

Сохраняются существующие ограничения размера, последовательности, частоты кадров и восстановление захвата. Для радио применяется отдельный бюджет аудитории и ранний выход при отсутствии валидных слушателей, чтобы не создавать лишние копии буфера.

### Клиент

`OrbitraVoiceChatSystem` отслеживает две клавиши:

- существующая `PushToTalk` для локального голоса;
- новая `RadioPushToTalk` для рации.

Текущий выбранный радиоканал должен быть доступен системе голоса через общий клиентский источник состояния селектора чата. Выбор не дублируется в отдельном независимом списке. При смене канала уже начатая передача завершается, а следующий кадр использует новый канал.

Радио-кадры поступают в отдельный поток воспроизведения или в отдельный режим существующего потока. Буфер имеет небольшой запас для сглаживания сетевого джиттера, ограниченную длину очереди и сброс старых кадров при переполнении. Радио не зависит от частоты кадров отрисовки.

Для эффекта рации использовать доступную клиентскую аудиоцепочку OpenAL/Robust. Эффект должен включать узкополосную окраску и лёгкий шум/искажение, а при отсутствии EFX безопасно откатываться к ограниченному gain без падения клиента. Эффект не должен менять исходный proximity-путь.

### HUD

Во время радио-передачи над персонажем показывается существующий микрофонный индикатор с отдельным состоянием рации. В нижней правой части игровой области отображается компактная карточка говорящего и название канала.

Позиция карточки вычисляется относительно активной `ViewportContainer`, а не полного окна. Для раздельного интерфейса она остаётся левее правой панели чата; для обычного интерфейса прижимается к правому краю экрана. Карточка ограничивается по ширине и обрезает длинные имена безопасно, не уходя за границы.

## Ошибки и отказоустойчивость

- Некорректный или неизвестный канал: кадр отбрасывается без исключения.
- Нет доступа к передаче: кадр отбрасывается, клиент получает локальное состояние `RadioUnavailable` только при необходимости визуального feedback.
- Получатель потерял гарнитуру во время разговора: следующие кадры ему не отправляются.
- EFX недоступен: воспроизведение продолжается без DSP с безопасным уровнем громкости.
- Потеря или перестановка UDP-кадров: sequence и текущая политика буфера отбрасывают устаревшие кадры, не блокируя поток.
- Долгая передача: ограничение очереди и периодический контроль underflow не допускают постоянного роста памяти и исчезновения звука после переполнения.

## Локализация и настройки

Добавить русские и английские строки для:

- названия `RadioPushToTalk`;
- состояния «передача по рации»;
- названия общего и выбранных отделов в HUD;
- отсутствия доступного канала;
- описания радиоголоса в настройках.

Существующий выбор микрофона, тест микрофона, громкость входа/выхода и текущий proximity-PTT не меняются.

## Проверка

Добавить или расширить тесты:

- сервер отклоняет неизвестный канал и канал без права передачи;
- сервер доставляет радио-кадр только слушателям с нужным каналом;
- `Common` работает при наличии базового радио;
- смена или потеря гарнитуры прекращает приём отдела;
- proximity-кадр не становится радио-кадром и наоборот;
- смена выбранного канала применяется к следующей передаче;
- буфер сбрасывает старые кадры и продолжает воспроизведение после underflow;
- карточка HUD не выходит за границы обычного и раздельного интерфейса.

Проверить YAML/локализацию и выполнить узкие сборки Shared, Client и Server, затем короткий runtime-smoke с двумя клиентами: один говорит в общий и отдел, второй имеет/не имеет соответствующий канал.

## Риски и решения

- Состояние селектора чата может быть доступно только внутри UI-контроллера. В таком случае вынести выбранный радиоканал в небольшой клиентский сервис/событие, не создавая второго селектора.
- Радио DSP зависит от поддержки EFX на машине клиента. Обязателен fallback без эффекта.
- Большой отдел может создавать больше адресатов, чем proximity. Использовать один неизменяемый сжатый payload на кадр и отправлять его через фильтр, не копируя данные для каждого получателя.
