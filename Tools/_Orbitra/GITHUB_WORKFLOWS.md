# GitHub Orbitra: проверки и история ревью

## Что запускается

- `Build & Test Debug`: сборка DebugOpt, `Content.Tests` и `Content.IntegrationTests`.
- `YAML Linter`: проверка игровых прототипов и локализации.
- `Orbitra Automation Tests`: тесты Discord-публикатора, истории ревью и правил описания PR.
  Выполняется на каждом PR в `master`, включая Draft, без фильтра по путям и без секретов.
- `Orbitra PR Policy`: проверяет заголовок и четыре обязательных раздела шаблона.
  Скрипт читается из базового SHA, чтобы PR не мог заменить собственную проверку.
- `Orbitra PR Audit`: на push после approval добавляет комментарий с авторами, отправителем,
  коммитами, файлами и ссылкой на diff. После merge добавляет итоговый комментарий.

Для тестирования автоматизации:

```powershell
python -m pip install PyYAML==6.0.3 requests==2.32.5
python -B -m unittest discover -s Tools/_Orbitra -p 'test_*.py'
```

Тесты подменяют сетевые вызовы. Они ничего не отправляют в Discord и не публикуют комментарии.

## Ручная проверка на тестовом PR

1. Создайте обычный PR в `master` с небольшим изменением документации и заполненным шаблоном,
   включая раздел «Авторы и вклад». Убедитесь, что запустились все четыре обязательные проверки.
2. Дождитесь успешных проверок. Другой участник с правом ревью должен одобрить PR;
   сохраните SHA одобренного коммита для сравнения.
3. Отправьте ещё одно небольшое изменение в ту же ветку. Проверьте, что старое одобрение
   снято, а `Orbitra PR Audit` оставил комментарий с отправителем push, авторами коммитов,
   изменёнными файлами и ссылкой на сравнение с одобренным SHA.
4. Дождитесь проверок нового SHA и повторного одобрения другим участником.
   Для проверки обязательности ревью не используйте административный обход правил.
5. Если изменение действительно принято, выполните merge и проверьте итоговый комментарий
   аудита. Само создание тестового PR не требует его слияния.

PR только с документацией не проверяет доставку в Discord: туда публикуются новые записи
игрового ченджлога. Отмечайте отдельно проверенные этапы; открытый PR без чужого approval
ещё не подтверждает работу аудита изменений после одобрения.

## Защита master

Подготовленный набор правил: `.github/orbitra/master_ruleset.json`.

- Слияние через PR с одним approval и закрытыми обсуждениями.
- Новый reviewable push сбрасывает старые approvals; последнюю отправку должен одобрить другой участник.
- Обязательны четыре проверки, перечисленные выше, от GitHub Actions; ветка должна быть актуальной.
- Запрещены удаление и force push для обычных участников.
- Администраторы репозитория имеют явное право обхода (`RepositoryRole: 5`, `always`).
  Это сохраняет возможность владельца обслуживать личный репозиторий. Обычный процесс всё равно через PR;
  наличие административного обхода означает, что эти ограничения не абсолютны для владельца.

Сначала доставьте workflows и скрипты в `master`, затем включите правила. Иначе обязательные
проверки ещё не существуют и обычные PR будут ждать их бесконечно. Файл JSON сам по себе
не меняет настройки GitHub. Импорт доступен в Settings → Rules → Rulesets либо через CLI:

```powershell
gh api repos/Endennsss/orbitra-station/rulesets --method POST --input .github/orbitra/master_ruleset.json
```

Перед созданием проверьте существующие наборы правил. Если `Orbitra master review` уже есть,
обновляйте его через `PUT .../rulesets/<id>`, не создавайте дубликат.
Проверить применение: `gh api repos/Endennsss/orbitra-station/rules/branches/master`.

## Как читать журнал

Журнал различает автора PR, автора git-коммита, отправителя push, ревьюера и выполнившего merge.
Авторство git берётся из метаданных коммита и не является доказательством личности.
Раздел «Авторы и вклад» и `Co-authored-by` нужны для соавторов, которые не имеют отдельных коммитов.
После squash сохраняйте исходный PR: журнал содержит его коммиты до squash.

Одобрение, автоматически снятое GitHub, восстанавливается для аудита через событие `review_dismissed`:
снятый `CHANGES_REQUESTED` не принимается за approval. При force push и недоступном сравнении
комментарий явно просит перепроверить весь PR. Неудачный запуск можно повторить: запись с тем же
номером PR и SHA не дублируется, существующие записи не редактируются.

Показываются первые 30 коммитов и 20 файлов; ссылка ведёт к полному сравнению GitHub.
Старые события, для которых PR уже продвинулся на другой SHA, пропускаются; актуальная запись
сравнивает весь накопленный diff с последним approval. Это не внешний неизменяемый audit log:
администратор может удалить комментарии, а неуспешный workflow требует повторного запуска.

`pull_request_target` читает только скрипт из базового SHA. Код PR и его артефакты не запускаются,
права ограничены чтением содержимого и записью в PR, Discord-секрет этому workflow не передаётся.
Итоги ревью и merge остаются на GitHub. Discord получает новые записи игрового ченджлога
и отдельное уведомление при открытии PR в `master`, включая черновики.

Документация: [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets),
[события снятого ревью](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#review_dismissed).
